# Live Trader 탭별 수동 검증 안내

기준일: 2026-09-06. 이 문서는 사용자가 프로그램을 직접 열고 한 단계씩 확인하기 위한 기록 양식이다. 자동 테스트 통과와 아래 실제 사용자 실습 완료는 따로 기록한다.

## 네 프로그램에서 Live가 담당하는 일

Stock Data Scraper는 검사한 데이터를 발행하고, Backtester는 그 데이터로 검증한 전략의 불변 저장본을 발행한다. Paper Trader는 선택한 전략·Instance·Portfolio를 실제 시간의 신호 관찰과 가상 체결로 검증하고 근거를 봉인한다. Live Trader는 그 근거와 현재 저장본을 대조한 뒤 별도의 계좌·배포·위험 한도·운용자 승인 안에서 실제 운용한다.

화면의 전략 흐름은 **백테스트 → 모의 검증 → 제한 실거래 → 실전 운용**이다. `주문 연결 시험`은 별도 기능시험이다. 연결 시험 성공이나 높은 검증 단계만으로 전략이 승급하거나 주문 권한이 열리지는 않는다.

현재 Paper 근거 확인은 읽기 전용이다. `VERIFIED_READ_ONLY`는 현재 저장본과 봉인 근거의 일치만 뜻한다. Live 후보 등록, 최초 제한 실거래 심사·승인은 아직 준비 중이며 이 화면에서 실행할 수 없다. 준비되지 않은 감독형 코인 경로도 HOLD 사유와 잠금을 유지한다.

현재 일반 자동매매도 관찰 모드만 지원하며 최종 실주문 전송은 차단돼 있다. 실행 범위가 확인되지 않으면 시작 버튼도 활성화하지 않는다. 설정 저장이나 다른 점검의 통과만으로 이 미지원 상태를 해제할 수 없다.

## 실습 전에 적을 것

- [ ] 실행 파일/소스 버전과 확인 시각을 기록했다.
- [ ] 상단의 현재 Deployment, 실거래 잠금, Preflight, 신규 진입, 위험 증가 주문, Broker 전송, 전역 Kill 표시를 읽었다.
- [ ] 기존 실행 세션·미체결·보유 포지션 유무를 확인했다. 알 수 없는 항목은 `미확인`으로 적었다.
- [ ] 이번 실습은 화면과 조회부터 진행한다. 실제 주문·취소·시작·중지·복구는 사용자가 목적과 현재 상태를 확인한 별도 단계에서 실행한다.
- [ ] 계좌번호는 식별에 필요한 끝자리만 기록하고 API key/secret, 승인 토큰, 일회용 문구는 기록하지 않는다.

실거래가 진행 중이면 실습 때문에 설정·선택 대상·운용 모드를 바꾸지 않는다. 기존 세션을 먼저 확인하고 그 세션의 정식 중지·대조 절차를 따른다. 이 문서의 빈칸이나 체크 표시는 서버의 승인·대조 결과를 대신하지 않는다.

## 첫 실습: 연결·설정

목표는 **설정이 읽히고, 저장 상태·실제 연결·주문 권한을 구분해서 이해할 수 있는지** 확인하는 것이다. 이번 단계에서 실주문 라우트를 켜지 않는다.

1. `연결·설정`을 연다. 읽는 중·읽기 실패·빈 설정이 구분되는지 확인한다. 서버 연결이 끊겼다면 표시 오류를 적고 저장을 진행하지 않는다.
2. `브로커 실계좌 연결`에서 현재 사용할 그룹 하나를 고른다. 주식/ETF는 KIS, 코인은 Binance 또는 Upbit다. 연결하지 않은 다른 그룹의 미설정을 현재 그룹의 성공으로 해석하지 않는다.
3. 각 항목의 이름·설명·저장 여부를 확인한다. 비밀 입력란이 비어 있어도 `저장됨` 표시가 있으면 기존 값이 숨겨진 상태다. 확인만 하려면 다시 입력하지 않는다.
4. `READY`, `DONE`과 같은 설정 상태는 항목 구비 여부를 뜻할 수 있다. 실제 계좌 조회의 성공 시각·오류 여부를 함께 확인해야 연결 성공으로 기록한다. 현재 화면에 그 근거가 없으면 `미확인`으로 남긴다.
5. 설정을 바꿔야 할 때만 해당 그룹에 필요한 값을 입력한다. 기본 주소·계좌 종류·환경을 사용자 자신의 계좌 설정과 대조한다. `실거래 잠금` 그룹의 주문 허용은 이 단계에서 변경하지 않는다.
6. 필요한 변경이 있을 때만 `연결 설정 저장`을 누른다. 진행 중 중복 클릭을 하지 않고 성공/실패 응답을 확인한다. 저장 실패나 빈 응답을 완료로 적지 않는다. 저장 직후 비밀 입력값이 화면에 남지 않는지 확인한다.
7. 탭을 나갔다 돌아와 비밀값이 다시 표시되지 않고 설정 여부가 유지되는지 확인한다. 상단의 실거래 잠금·신규 진입·Broker 전송 상태도 다시 읽는다. 설정을 저장했다고 주문이 허용되어서는 안 된다.
8. `설정·Runtime 자체 검사`의 최근 진단 시각과 차단·주의 항목을 읽는다. 진단 이력이 없으면 `미실행`이다. 항목을 누르면 관련 화면으로 이동하는지 확인한다. 일반 운용 동선은 1회 전략 진단 실행에 의존하지 않는다.
9. 화면·레이아웃 설정은 원하는 항목 하나만 바꾸고 글자·대비·스크롤·버튼 접근성을 확인한다. 설정 변경 전후에 현재 Deployment나 운용 모드가 바뀌지 않았는지 확인한다.
10. Telegram 표시가 필요한 경우 해당 패널의 연결 결과를 확인한다. 패널은 Bot API와 채팅 접근 권한을 조회할 수 있으며 `CONNECTED`와 알림 비활성 `MUTED`는 다르다. 이 확인은 시험 메시지 전송이 아니다. 실패하면 이유와 확인 시각만 적는다.
11. `계좌·잔고`로 이동해 현재 조회 시각과 연결 결과를 확인한다. 명시적으로 새로고침했다면 대기·성공·실패 중 어떤 결과인지 기록한다. 실패·부분 응답·연결 중 상태가 잔고 0 또는 대조 완료로 표시되면 검증 실패로 기록한다.
12. `시작 점검`으로 돌아와 연결·대조 관련 표시가 같은 사실을 나타내는지 확인한다. 미체결·대조 필요가 남았다면 이를 해결한 뒤 다음 실습으로 진행한다.

## 이후 탭별 실습

### 시작 점검 → 운용 전략

- [ ] 연결·대조·시세·배포 확인 항목을 읽고 남은 작업을 구분한다. 체크리스트의 완료 표시는 실제 조회·승인 근거와 일치해야 한다.
- [ ] 현재 Deployment와 전략 이름·ID·버전을 기록한다. 검색·필터·탭 이동만으로 현재 대상이 변경되지 않는지 확인한다.
- [ ] Paper 검증 근거를 명시적으로 새로고침한다. 처음부터 근거가 있는 것처럼 표시하거나 자동으로 등록하지 않아야 한다.
- [ ] 근거 일치, 없음, 손상, 오래된 버전, 중복, Instance 불일치가 구분되는지 확인한다. 확인 전용 후보에 실행/승인 권한이 붙지 않아야 한다.
- [ ] 제한 실거래 대기와 검증 완료를 구분한다. 등록·최초 심사 등 준비 중 단계는 사유를 적고 남겨 둔다.

### 실거래 운용

- [ ] `실행·중지`에서 runtime의 실행 여부, 최근 heartbeat, 프로필, 대상과 모드를 읽는다. 미관측 heartbeat를 정상으로 적지 않는다.
- [ ] `한도·안전장치`에서 자본·손실·주문·신규 진입 상태를 확인한다. 미확인 사용량을 0으로 가정하지 않는다.
- [ ] `운영 체크리스트`에서 위험 한도·알림·수동 개입을 실제로 검토한 항목만 확인/해제한다. API·계좌 및 포지션 대조는 자동 항목이라 직접 체크할 수 없어야 한다. 수동 저장은 기존 Preflight를 무효화하므로 실행 전에 다시 검사한다.
- [ ] 가용성 표시와 버튼 상태를 비교한다. HOLD·미연결·승인 미완료 경로는 시작할 수 없어야 한다.
- [ ] 이 문서의 화면 실습만으로 시작·잠금 해제·위험 증가 설정을 실행하지 않는다. 실제 제한 실거래는 사용자가 현재 계좌·대상·한도·종료 계획을 확인한 별도 단계에서 진행한다.

### 계좌·잔고 → 주문·체결

- [ ] 계좌·포지션 조회의 브로커·최근 시각·성공 범위를 확인한다.
- [ ] 미조회·오래된 조회·부분 실패·체결 동기화 실패를 구분한다. 새로고침 실패 후 과거 데이터가 남아 있다면 최신 정상 데이터처럼 보이지 않아야 한다.
- [ ] 브로커 사실과 내부 원장의 불일치, 작업 중 주문, 원인을 알 수 없는 주문은 대조 필요로 유지한다.
- [ ] 기존 주문 하나가 있다면 동일 주문 ID의 상태·체결량·수수료를 관련 화면과 대조한다. 없으면 `주문 없음`으로 기록하고 실습용 주문을 만들지 않는다.

### 실행 기록

- [ ] `운영 이력`에서 앞선 설정 변경이나 실패 기록을 찾는다. 기록이 없다면 조회 조건과 기록 유무를 구분한다.
- [ ] `상세 로그`에서 같은 시각·세션·주문과 연결되는 오류를 확인한다. 기술 로그가 없어도 운영 성공으로 추정하지 않는다.
- [ ] 화면·로그·복사 내용에 API secret이나 일회용 승인 자료가 포함되지 않는지 확인한다.

### 주문 연결 시험

- [ ] KIS·Upbit·Binance의 지원 범위와 현재 가용 여부를 읽는다. 미완료/HOLD/관측기 미준비는 잠금 사유와 함께 남아 있어야 한다.
- [ ] 기존 세션이 있다면 실행 중·정리 중·대조 필요·완료를 구분한다. 중단된 세션을 새 실행으로 덮지 않는다.
- [ ] 시험 결과가 `승급 제외`임을 확인한다. 성공 기록을 Paper 검증이나 전략 수익성 근거로 바꾸지 않는다.
- [ ] 실제 주문·중지·복구는 사용자가 해당 기능시험의 별도 승인·시간·주문/손실 한도·정리 조건을 확인한 때만 수행한다. 화면에 버튼이 보인다는 사실은 실행 승인 자체가 아니다.

## 이번 구조 정리의 반영 범위
