# 네 프로그램 구조와 Live Trader 검토

검토일: 2026-09-06. 기준 소스는 develop `8afc130`과 기존 미커밋 감독형 작업이며 이번 변경을 별도로 구분한다. 이 문서는 설계 의도, 확인한 코드 동작, 자동 시험과 사용자의 실제 실습을 구분한다.

## 최종 목표와 책임

최종 목표는 검증된 정확한 전략 버전을 정해진 계좌·자본·손실 한도 안에서 실제 운용하고, 모든 주문의 결과와 중단·복구 상태를 추적할 수 있게 하는 것이다. 자동매매를 켜거나 과거 수익률을 보는 것만으로 목표를 달성한 것은 아니다.

| 프로그램 | 만드는 결과 | 다음 프로그램이 확인할 것 |
|---|---|---|
| Stock Data Scraper | 품질·계보 검사를 통과한 PUBLISHED Dataset Version | 파일·manifest/hash, 완료된 봉, 최신 발행 상태 |
| Backtester | 과거 검증을 거친 불변 Strategy/Instance/Portfolio | 데이터 계보, 파라미터와 저장본 ID/hash, 검증 근거 |
| Paper Trader | 같은 버전의 실시간 신호·가상 체결·원장·대조·안정성 근거 | 봉인 publication-v2, 실행 범위와 현재 저장본 일치 |
| Live Trader | 승인된 실계좌 실행과 주문·체결·위험·복구 이력 | 현재 Deployment와 Preflight, 계좌 사실, 실행 가능 경로, 주문마다 안전 조건 |

책임 분리는 적절하다. 데이터 수집과 과거 최적화 기능을 Live에 다시 넣을 이유가 없다. 기능시험은 배선 확인이며 전략 승급 근거와 구분한다. 공통 검증 단계는 백테스트 → 모의 검증 → 제한 실거래 → 실전 운용이다.

구현은 React/Vite → Python HTTP API → 상태·승인·원장·브로커 어댑터이며 pywebview/PyInstaller가 데스크톱 배포를 담당한다. `packages/design`, `packages/trading_runtime`, `packages/trading-contracts`, `packages/strategy-core`를 공유한다.

## 최종 완주 전에 남은 필수 작업

1. **Paper → Live 최초 인수와 심사**: 현재 inbox는 `VERIFIED_READ_ONLY`, `canImport=false`, `authorizationGranted=false`다. 공유 DeploymentStore의 앱 간 동시 변경 보호(CAS/공통 잠금), 정확한 버전의 초회 등록, draft/OFF 후보의 심사·승인 및 실패 복구를 하나의 일관된 절차로 연결해야 한다. 화면 버튼만 추가하면 충분하지 않다.
2. **일반 continuous 최종 dispatch**: `RUNTIME_MODE_LOCK` 보유 상태에서 실제 브로커 전송이 `CONTINUOUS_FINAL_DISPATCH_LOCK_ORDER_UNAVAILABLE`로 차단된다. 주문 직전 상태 변경·Kill·권한 철회·동시 실행을 보장하는 잠금 순서와 전송 계약을 완성하고 검증해야 한다. 이번 변경은 표시와 시작 가드이며 잠금을 해제하지 않는다.
3. **감독형 코인 운용**: 현재 production/network release가 닫혀 있고 Upbit observer의 frozen broker adapter가 준비되지 않았다. 기존 사전 준비·권한·종료 작업을 별도로 완성하고 모의 시험 후 실제 제한 범위를 검증해야 한다.
4. **Portfolio와 Futures 지원 범위**: Paper의 Portfolio Finance 비교·전체 Signal parity가 미완성이다. Live의 cross-broker Preflight와 Futures 진입+거래소 보호 STOP 계약도 아직 지원 범위에 제한이 있다. 단일 전략의 성공을 이 경로의 통과로 대신하지 않는다.
5. **실계좌 수동 검증**: 연결, 현재 배포, 원장 대조, 한도, 중단·복구와 실제 주문 결과는 사용자의 탭별 실습으로 확인해야 한다. 자동 UI 시험만으로 실전 운용 가능 판정을 내리지 않는다.

`state.py`와 `App.jsx`의 규모도 후속 유지보수 과제다. 이번에는 표시 projection을 순수 모듈로 분리하고 죽은 코드를 제거했다. 주문 잠금과 전역 상태를 한꺼번에 분리하는 대형 리팩터링은 기존 감독형 변경과 섞지 않고 기능별 회귀 근거를 확보하며 진행한다.

## 검증 범위

이번 변경의 자동 검증은 실제 JSX/API의 모의 fetch 회귀, 실행 가용성·Canary 집계·대조 표시 계약, 실제 Python 함수의 AST 격리 회귀, production bundle의 오프라인 Edge 화면 시험과 데스크톱 배율 계약을 사용한다. 오프라인 서버는 모든 API를 대체하거나 거부하며 실제 Python 앱, 브로커 계좌, 주문, Telegram과 연결하지 않는다.

EXE는 현재 작업폴더에서 패키징한다. 이전부터 남은 미커밋 감독형 코드도 포함되므로 이번 검토 커밋만의 바이너리라고 해석하지 않는다. 최종 시험 결과와 산출물은 인쇄용 기록 및 Notion 요약에 남긴다.

최종 결과:

- `npm run test:workflow`: 80/80 통과. 계좌 대조 회귀 스크립트는 여러 실패·복구 시나리오를 포함한 1개 test 항목으로 집계된다.
- Python AST 격리: workflow projection 8/8, 실행 가용성 4/4 통과. 실제 사용자 환경·DB를 초기화하지 않았다.
- `npm run ui:offline`: 1280/1920 폭의 8탭, 내부 risk/audit 경로, 체크리스트 저장, 승급·미지원 시작 차단, 가로 넘침 0, 런타임 JS 오류 0, 브로커 I/O 0.
- production build 및 100/125/150% 배율·클릭 계약 통과. 첫 배율 실행은 임의 포트 5061의 브라우저 차단으로 중단됐고 새 임의 포트로 재실행해 통과했다.
- `release_pending/LiveTrader.exe`: 22,005,532 bytes, SHA-256 `d6b570584531b15d82b30e99d0a08628d598ee50ddf423671708fd3787a912cd`.
- EXE를 실행하지 않고 내장 화면 6파일의 바이트 일치와 state/execution_availability/paper_candidate_inbox 모듈 포함을 확인했다. 기존 release는 유지했다.

## 사용자와 이어갈 순서

[탭별 수동 검증 안내](manual-tab-validation.md)를 사용한다. 먼저 연결·설정에서 저장 상태와 실제 연결을 구분한다. 이후 시작 점검 → 운용 전략 → 계좌·잔고 → 실거래 운용의 한도·안전장치 → 주문·체결 → 실행 기록 순으로 목적·행동·결과를 기록한다. 주문 연결 시험과 실제 운용 시작은 지원 경로·대상·한도·종료 조건이 갖춰진 단계에서 별도로 다룬다.

각 단계의 정상 기준이 충족되면 다음으로 진행하고, 실패하면 재현 조건과 오류를 남긴 뒤 수정한다. 의도된 미지원 차단은 차단 유지로 기록한다.
